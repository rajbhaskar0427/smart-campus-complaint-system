## ABSTRACT

Students, faculty members, laboratory instructors, and residential hostel occupants in higher technical educational institutions routinely encounter physical facility defects, including malfunctioning electrical fixtures, leaking plumbing pipes, damaged classroom furniture, defective network ports, and non-functional air conditioning units. Traditionally, campus maintenance grievances are managed through manual logbooks placed at estate administrative desks, handwritten paper slips, telephone calls to hostel wardens, or informal verbal requests. This fragmented approach frequently leads to misplaced complaints, delayed repairs, duplicate reporting, lack of technician accountability, and zero visibility into resolution progress.

The Smart Campus Complaint System is proposed as a lightweight, centralized web application that brings facility grievance lodging and resolution tracking into a unified, student-oriented platform. The intended first version uses Python 3 and Flask for server-side request processing, standard HTML5, CSS3, and JavaScript for the responsive browser interface, and SQLite for structured relational data storage. Its principal modules are user authentication and profile management, categorized complaint intake (covering Electrical, Civil, Plumbing, IT Infrastructure, and Furniture), administrative triage and technician allocation, repair lifecycle milestone tracking, and an estate dashboard that summarises facility maintenance records across campus blocks.

The report presents the formal problem definition, operational objectives, related work, functional and non-functional specifications, feasibility analysis, logical architecture, data-flow and entity-relationship models, module designs, implementation approach, and a structured verification plan. Security considerations include PBKDF2 password hashing, secure session management, parameterised SQL queries, input sanitization, and role-based data access controls. The first version focuses on core software-driven ticketing workflows and does not claim automated IoT telemetry, predictive hardware failure sensors, or drone-assisted structural inspections. The accompanying reference code and test cases require local execution and verification before results can be stated as completed. The expected contribution is a practical, maintainable system for consolidating campus complaint data and improving visibility of resolution progress across collegiate campus infrastructure.

# CHAPTER 1: INTRODUCTION

## 1.1 Background

Campus facility management and maintenance grievance redressal represent vital operational pillars supporting academic activities in collegiate environments. Higher educational institutions maintain extensive physical infrastructure across academic blocks, administrative wings, computer laboratories, lecture halls, and residential hostels. Daily campus life involves continuous utilization of facilities, resulting in routine maintenance requirements such as repairing damaged electrical fixtures, fixing leaking plumbing pipes, rectifying malfunctioning laboratory air conditioners, resetting broken network ports, and repairing damaged seating furniture. Each incident generates operational information that must be tracked from initial reporting through diagnosis, work allocation, field repair, and user verification. A complainant needs to know whether an issue was acknowledged, when a technician was assigned, what actions were taken, and when normal utility service was restored.

In practice, campus facility grievances are frequently recorded in disparate, uncoordinated locations. A student may report a hostel room fan failure in a physical ledger at the warden's desk, a faculty member may send a message to the estate supervisor regarding an air conditioning issue in a tutorial room, a laboratory assistant may phone the electrical department directly, and a student may submit an informal message to a campus group. None of these individual channels is inherently unsuitable, but the information becomes fragmented when several tools are used without a single organising structure. A student has to switch between locations, update the same detail more than once, and mentally combine records before understanding overall progress.

The central idea of the Smart Campus Complaint System is to bring everyday campus maintenance records into one web application. A centralised tracker does not replace the physical effort required to physically complete repairs; instead, it reduces the administrative overhead of remembering, transcribing, and organising that effort. A common dashboard can show whether maintenance tasks are completed or pending, preserve technician resolution records, and provide a compact view of work-order tickets and their current states.

The proposed application is deliberately modest in scope. It is planned for an individual student project and uses technologies that are approachable for a second-year Bachelor of Technology student: Python 3 for programming, Flask for request handling, HTML/CSS/JavaScript for the interface, and SQLite for local data storage. Flask supports URL routing and template rendering, while the Python sqlite3 module provides a lightweight interface to SQLite databases [3], [4]. This combination supports a manageable mini project without requiring a separate database server.

The system is organised as a set of connected modules. Student authentication and profile management identify the user and provide basic personal context. The grievance intake tracker stores complaints by category, location, and status. The technician resolution module captures assigned trade staff, inspection date, parts replaced, and diagnostic notes. The administrative triage module records trade department, priority, target deadline, and dispatch details. The dashboard draws from these records and displays summaries instead of requiring estate staff to inspect each physical ledger independently.

The project also provides a useful setting for learning core software-engineering concepts. Requirements are translated into functional and non-functional specifications; the database is modelled using entities and relationships; routes implement create, read, update, and delete operations; input validation reduces invalid records; and testing checks whether a feature behaves as expected. The same project introduces basic web-security responsibilities, including password hashing, session management, parameterised queries, and ownership checks for user-specific records. Security is relevant because the system stores personal student details, location data, and maintenance records.

The scope is student-side tracking rather than automated industrial facility management. Research on computerized maintenance management systems (CMMS) explores predictive failure analytics, while recent facility IoT research evaluates machine-learning methods for sensor-based anomaly classification [1], [2]. These are related areas, but they solve different problems and require datasets, evaluation methods, and governance beyond the present mini project. The first version therefore does not claim to integrate IoT vibration sensors, predict equipment breakdowns automatically, or dispatch robotic maintenance. Such capabilities are more appropriate as future extensions after the basic record-management workflow is dependable.

## 1.2 Problem Statement

Students, faculty members, and campus residents need to manage several types of maintenance grievances over an academic semester. The information includes defect descriptions to resolve, locations and room numbers, urgency levels, technician assignments, scheduled repair dates, and work-order resolution outcomes. When the records are stored in separate notebooks, spreadsheets, and messages, a student or estate manager may find it difficult to form a complete and current view of the work already completed and the work still pending.

The practical problem is not simply the absence of a digital tool. A spreadsheet can store many records, and a messaging group can broadcast notices, but estate personnel must manually create and maintain the connections between complaint records, technician assignments, and verification updates. Fragmented records can lead to duplicated effort, incomplete updates, delayed follow-up, and difficulty reviewing progress. Manual consolidation also takes time that could otherwise be used for active campus maintenance.

The proposed solution is a centralised web application in which a student can maintain a profile, enter facility maintenance complaints, track work-order progress, record resolution verification, and review the information through a dashboard. The application should provide straightforward forms and lists, preserve records in one database, and show simple counts or summaries that support planning. The system is intended to assist organisation and visibility; it cannot guarantee physical repair speed or prevent hardware deterioration.

The operational friction caused by manual logging has tangible repercussions on residential student life. When hostel electrical fixtures malfunction—such as ceiling fans failing during peak summer examination periods—the absence of an immediate digital acknowledgement creates acute anxiety among residents. Similarly, unaddressed plumbing leakages in high-occupancy hostels quickly escalate into structural water damage and sanitary hazards, requiring reactive repairs rather than preventative maintenance.

The project problem can therefore be stated as follows: how can a lightweight, student-oriented web system be designed to consolidate campus maintenance grievances, technician allocation records, and work-order application statuses in a maintainable and secure manner, while remaining small enough for an individual second-year mini project? The solution must balance usefulness with realistic time, skill, and resource constraints.

## 1.3 Objectives

The overall objective is to design and develop a simple web application that centralises the information students and estate staff use during campus maintenance management. The system should be easy to navigate, keep records persistent between sessions, and provide a practical summary of maintenance activities and work-order progress.

## 1.4 Scope of the Project

The scope includes the student-facing and estate maintenance workflows described in the synopsis. A student can create an account, sign in, update basic profile information, lodge maintenance grievances, track work-order records, maintain assigned technician updates, and view a dashboard. These workflows share a local SQLite database and are accessed through a Flask web application. The design focuses on clarity and maintainability rather than high-volume multi-institution use.

The complaint intake tracker is intended for personal and campus-level grievance planning. Each complaint can contain a short title, category, campus location (block, floor, room), target urgency state, and optional note. The technician resolution tracker records actions entered by estate supervisors or staff. The first version does not connect to external telemetry sensors, import automatic diagnostics from smart meters, or infer failure severity automatically. Its output depends on the accuracy and completeness of information entered by the user.

The work-order allocation tracker records maintenance trade information entered by the estate supervisor. It can preserve a department name, designated technician, scheduled inspection date, application status, outcome, and remarks. It does not retrieve live inventory catalogs, submit procurement purchase orders, verify supplier warranties, or synchronise with external municipal utility offices. Such integration would require authenticated external interfaces, reliable data agreements, and additional security considerations.

The dashboard is designed to present simple descriptive summaries such as total complaints, completed and pending repairs, number of technician allocations, average resolution days across completed work orders, and counts by application status. Summary values are indicators of stored data rather than objective measures of estate engineering health. A higher resolution percentage does not necessarily mean campus facilities are completely defect-free, and turnaround metrics should be interpreted in the context of spare part availability and repair complexity.

The application is planned for local development and demonstration using a laptop that meets the modest hardware specification in the synopsis. The use of SQLite avoids a separate database server for a single-user or small demonstration context. If the system is later used by a larger campus group, the database, hosting model, backup approach, logging, and access-control model would need review. Deployment to a public server is outside the initial scope.

The project excludes automated computer-vision defect detection, IoT telemetry sensor networks, predictive failure analytics, automated spare parts ordering, and advanced machine-learning models. This is an intentional boundary. Those features introduce sensor calibration, dataset quality, hardware maintenance, bias evaluation, privacy, and explainability requirements that cannot be addressed merely by adding a software library. The first version prioritises the reliable capture and display of records; richer features can be considered only after the underlying data model and core workflows are stable.

The project is also not a substitute for the institute’s official emergency response protocols. Critical infrastructure emergencies, such as gas leaks, electrical fire hazards, major pipe bursts, or structural damage, remain subject to immediate direct communications with campus security and emergency teams. The complaint tracker is an operational organisation aid for routine and scheduled maintenance. Users should report hazardous conditions through emergency channels immediately before filing digital records.

Data privacy and student identity protection constitute an essential aspect of the campus grievance scope. Although the portal manages maintenance defects, tickets contain personal identifiers such as room numbers, hostel names, student roll numbers, and contact details. The system enforces strict tenant isolation and role-based permissions to ensure that students can only inspect grievances they personally submitted, while maintenance personnel access only work orders relevant to their trade.

Institutional estate operations in collegiate settings involve distinct communication hierarchies between hostel wardens, department heads, maintenance technicians, and students. By maintaining a clean separation between routine maintenance tracking and formal academic disciplinary procedures, the application provides an objective, transparent record of physical repairs without intruding upon departmental academic governance.

# CHAPTER 2: LITERATURE REVIEW / EXISTING SYSTEM

## 2.1 Review of Related Work

Digital facility and grievance management systems have increasingly used structured complaint records, issue classifications, and tracking techniques to support parts of campus infrastructure operations. A systematic review by Ertuğrul and Bitirim examines organizational workflow and ticketing systems, classifies their approaches, and discusses open issues and challenges in the field [1]. The review illustrates that facility-related software can use structured information to help organise maintenance requests and room data, but automated triage functionality is a distinct research problem rather than a basic database operation.

Facility management systems may apply rule-based, priority-driven, hybrid, knowledge-based, or SLA-aware approaches. These methods differ in the evidence they use and the assumptions they make. Rule-based approaches compare attributes of a complaint (such as location and category) with maintenance schedules; priority-driven approaches use escalation thresholds; hybrid methods combine more than one signal. Such designs can require a sufficient amount of appropriately structured information and a way to evaluate repair urgency. These requirements are beyond the first release of the current project, which does not attempt to rank municipal contractor tenders.

Related research also examines automated defect screening. Hamid and colleagues describe an ensemble machine-learning approach for maintenance request classification and report experimental evaluation on benchmark and curated datasets [2]. The article demonstrates that automated classification can involve model comparison, data preparation, evaluation metrics, and robustness checks. It does not mean that every campus-tracking application needs an AI classification model. For the current scope, students enter and review their own records; there is no automated classification of image attachments or contractor recommendations.

The technical foundation of the proposed system is supported by the documentation for Python and Flask. Flask’s quick-start guide explains application creation, URL routing, templates, request handling, and session use [3]. These mechanisms are suitable for separating browser-facing pages from the server-side functions that process forms and read or write records. Flask also relies on template escaping for typical HTML templates, although developers must still avoid unsafe rendering of untrusted input and should understand the limits of development-mode configuration [3].

Python’s sqlite3 module exposes an interface for working with SQLite, a lightweight disk-based database that does not require a separate database server [4]. SQLite supports a useful subset of SQL for table creation, query execution, filtering, joining, and aggregation [5]. For

an individual mini project, these features are adequate for storing users, complaint tasks, technician records, and work-order entries. Parameterised statements should be used when user-provided values are included in SQL queries, and foreign-key relationships should be designed to preserve record ownership and integrity.

Security guidance is especially relevant because the system uses login credentials and personal records. The OWASP Password Storage Cheat Sheet advises against storing passwords in plain text and recommends slow password-hashing methods designed for that purpose [6]. In the proposed reference implementation, a framework-supported password-hashing function is used rather than storing the original password. Session protection, secret-key configuration, validation, parameterised SQL, and per-user record filters are additional design considerations; a classroom prototype should not be described as production-secure without a dedicated review.

The literature and documentation inform different parts of this project. The facility studies provide context for structured grievance and maintenance information, while the official technology documentation supports the choice of tools and implementation practices. The project contribution is intentionally narrower: it combines the student’s own complaint records and work-order tracking in one accessible interface. The value to be assessed is whether the proposed system helps organise these records reliably, not whether it outperforms automated scheduling algorithms.

## 2.2 Existing System

A common existing approach is manual tracking. A student writes defect details and locations in a notebook or physical estate ledger, notes technician visits separately, and maintains follow-up requests in a spreadsheet or a set of messaging threads. Manual records are quick to start and do not require software installation. They can also be tailored to the student’s habits. However, they depend on consistent updating and may not provide an automatic summary across all categories of information.

Spreadsheet-based tracking is more structured than scattered notes because rows and columns can store dates, locations, categories, statuses, and comments. An estate clerk can sort records and use simple formulas. The limitation is that the user must create the schema, establish valid values, maintain formulas, and coordinate related sheets. For example, an estate supervisor may use separate sheets for electrical defects, plumbing issues, and carpentry but have no integrated dashboard that updates from all three without additional configuration.

Calendar and reminder tools are useful for time-specific events. They can show a scheduled maintenance inspection or an allocation deadline, but they generally do not provide a unified history

of repairs, task completion, and resolution outcomes. A general task-management application may store activities but not include a purpose-built record for technician notes or campus maintenance stages. Users may therefore need several tools even when each tool performs its individual function well.

Institutional estate portals and commercial facility management websites provide authoritative information about university assets, budget allocation, contractor procurement, and major renovations. Their focus is generally the official administration or institutional financial workflow. They may not offer a personal, accessible view of day-to-day student complaints and localized repair progress across individual hostel rooms. The proposed system is not intended to replace enterprise ERPs; it maintains a lightweight student-side record to complement information managed by campus administration.

General facility helpdesk platforms may hold tickets and technician assignments, and some provide automated routing or SLA monitoring features. These systems can be useful when an institution is ready to deploy enterprise software, but the workflow and licensing fees may exceed what an individual department requires. Integrating external commercial services can also require account permissions, APIs, network access, and compliance with terms. The first version avoids such dependencies and relies on direct local records.

The existing approaches have strengths and should not be treated as universally ineffective. Paper registers are flexible, spreadsheets are familiar, calendars support scheduling, and official estate offices manage major civil projects. The gap addressed here is the lack of a single lightweight student-centred location that combines the specific categories identified in the synopsis without requiring external integrations or complex configuration.

## 2.3 Gaps Identified

The first gap is fragmented data. Complaint details, technician visits, and resolution outcomes are often kept in different records. When each record is maintained independently, an estate clerk or student has to consolidate information mentally or manually. The proposed system uses one database and a shared dashboard to reduce the need for repeated checking across tools.

The second gap is limited visibility of resolution progress. A list of complaints does not automatically show a concise distinction between completed and pending work. A collection of technician logs may not be easy to review alongside those tickets. Simple summaries can make the current state more legible, provided that the dashboard defines its counts clearly and does not imply more than the underlying records support.

The third gap is the absence of a consistent resolution history. Defect titles may be recorded when an issue is logged, while later updates such as an inspection visit, spare parts requisition, completion, or user verification may appear in phone messages. A dedicated record allows a

student to update the status and preserve the outcome in one place. The system remains dependent on the student entering accurate and timely information.

The fourth gap is usability and setup overhead. General-purpose tools can be configured for almost any tracking problem but may require the estate staff or student to create worksheets, labels, formulas, or templates. A small application can provide predefined categories and forms for the intended workflow. This reduces setup effort but also makes the schema less flexible than a fully configurable tool.

The fifth gap concerns the boundary between tracking and intelligent automation. Research may offer methods for predicting equipment wear or automated image analysis [1], [2], but the presence of structured records is not by itself proof that an AI model is required. For a second-year mini project, a first release that establishes data quality, correct relationships, clear forms, and stable CRUD operations is a sound foundation before advanced analytics are considered.

The identified gaps translate into testable design choices: a single login-protected web application, a common data store, separate modules for complaints, triage, and technician updates, a dashboard driven by database queries, and basic validation to reduce malformed records. These choices are appropriate for the defined scope and can be evaluated with a functional test plan. The project should be judged against these limited requirements rather than against systems that provide capabilities outside its scope.

## 2.4 Proposed System

The proposed Smart Campus Complaint System is a web application in which the student uses a browser to access a set of connected functions. The browser displays forms and record lists, the Flask application handles requests and validates input, and the SQLite database stores records. A user must sign in before reaching personal pages. Each record is linked to the signed-in user so that one account cannot access another account’s complaints, technician notes, or administrative records through a manipulated URL.

The profile module stores basic user details, while the grievance management module supports adding, editing, marking resolved, and deleting complaints. The technician module stores the inspection label and technician notes. The department allocation module stores trade and assignment details alongside a status chosen from a controlled set. The dashboard reads current records and displays a brief overview. These modules share the same user identifier, avoiding the need to duplicate the student’s identity in each record.

The application follows a request-response workflow. When the student submits a form, the browser sends the submitted values to a Flask route. The route checks authentication and

validates the values, then executes the appropriate database operation using parameters rather than building SQL by string concatenation. The application displays a confirmation or validation message and returns the updated list. This pattern keeps the main logic easy to trace and suitable for introductory software testing, ensuring that untrusted user input is strictly treated as query literal data rather than executable SQL syntax.

The system incorporates an explicit resident verification and feedback loop to guarantee accountability before ticket closure. When a technician marks an assigned maintenance task as 'Resolved', the ticket does not automatically terminate. Instead, the complainant receives a notification prompt on their dashboard requesting physical inspection of the repaired facility. The resident can confirm successful repair by submitting a 1-to-5 star rating and optional comments, which formally advances the status to 'Closed'. If the repair is defective, the ticket can be reopened with explanatory notes.

The design emphasizes practical constraints and architectural separation of concerns. SQLite provides lightweight, zero-configuration persistence that is entirely sufficient for local demonstration and single-department campus trials. Flask provides a modular request dispatching framework without the steep learning curve and operational overhead of enterprise platforms. Standard HTML5, CSS3, and JavaScript deliver a clean, responsive presentation layer accessible across modern desktop and mobile browsers.

The proposed system is expected to improve the organisation of records, eliminate misplaced physical chits, establish clear technician accountability, and provide a convenient overview of maintenance progress across campus facilities. These represent intended functional benefits that must be substantiated through rigorous local testing under controlled conditions. The report maintains a clear distinction between intended architectural design, accompanying source code, and empirical verification evidence collected after running the application on a local development workstation.

The architectural design of the proposed platform prioritizes cross-device accessibility and defensive network security. Recognizing that the vast majority of campus grievances are submitted by students using mobile smartphones immediately upon discovering a physical defect, the presentation layer implements mobile-first responsive viewport formatting. Touch-friendly selection controls, enlarged tap targets for trade categories, and dynamic accordion views ensure that students can log grievances with equal facility on mobile handsets as on desktop workstations. At the application controller boundary, requests are secured with Cross-Site Request Forgery (CSRF) tokens, preventing unauthorized third-party scripts from submitting fraudulent complaint records on behalf of authenticated students.

# CHAPTER 3: SYSTEM ANALYSIS AND DESIGN

## 3.3 System Architecture

The architectural design of the Smart Campus Complaint System is based on the classical Three-Tier (Presentation, Application Logic, and Data Persistence) architectural pattern. This multi-layered structure ensures strict separation of concerns, decoupling user interface rendering, core transactional business logic, and relational persistence. Separation of concerns improves code maintainability, simplifies unit testing, and permits future extensions—such as substituting SQLite with MySQL or deploying a mobile client—without modifying core domain processing rules.

The Presentation Tier encompasses the client-side user interface executing within the student or administrator's web browser. Built with semantic HTML5, modular CSS3 styling, and responsive layout grids, this layer handles user input capture, form validation feedback, interactive milestone progress displays, and asynchronous UI updates. Templates are authored using the Jinja2 engine, which securely renders dynamic server-side data into HTML pages while automatically escaping untrusted input to defend against Cross-Site Scripting (XSS) vulnerabilities.

The Application Logic Tier is powered by the Flask microframework running on Python 3. It serves as the central controller orchestrating incoming HTTP request dispatching, session authentication, role-based authorization verification, input sanitization, grievance triage routing, and SLA compliance monitoring. Route handlers enforce granular security decorators, guaranteeing that unauthorized requests are intercepted before reaching transactional database layers.

The Data Persistence Tier provides reliable relational storage using SQLite for local development and demonstration, with seamless compatibility for production MySQL database servers. It manages relational tables, enforces foreign key constraints, preserves referential integrity across grievance logs, and executes ACID-compliant transactions to guarantee persistent state consistency. ## 3.5 Technology Stack

The activity diagram in Fig. 3.6 details the sequential operational decisions and state transitions executed from grievance inception to definitive closure. When a student submits a grievance, the application executes synchronous server-side input validation. If mandatory fields—such as category, location, and description—are missing or malformed, the system re-renders the intake form with targeted error alerts. The lifecycle state machine incorporates automated SLA countdown monitoring. If a work order exceeds its deadline without transitioning to 'Resolved', the administrative dashboard automatically escalates the ticket with an overdue badge, prompting supervisory intervention. This closed-loop tracking ensures that maintenance requests are resolved promptly and transparently.

Section 3.6.1: Database Indexing, Foreign Key Cascade Policies, Transaction Boundaries, and Relational Integrity Constraints. The operational stability of the Smart Campus Complaint System relies on disciplined relational integrity enforcement and optimized query execution paths. In high-density campus environments where hundreds of students lodge grievances concurrently, database query efficiency and transactional isolation prevent application bottlenecks and race conditions. To guarantee optimal performance during dashboard rendering and administrative filtering, composite B-tree indexes are established on frequently queried column combinations, specifically (user_id, status) on the complaints table to accelerate personal ticket retrieval, and (department_id, status) to speed up trade triage dispatch queues.

Foreign key cascade rules are configured with rigorous defensive constraints. While modern database engines permit cascading deletions across related child tables, the complaint management domain strictly disallows the automated deletion of historical grievance records. Consequently, foreign key links from complaints to users and departments implement ON DELETE RESTRICT constraints. If a student account or departmental profile is deactivated, the associated historical complaint records remain permanently intact, safeguarding institutional auditability. In contrast, ephemeral session tokens and cached query filters implement ON DELETE CASCADE to clean up temporary state automatically.

Transaction boundaries are enforced using atomic commit and rollback protocols. State mutations involving multiple database tables—such as updating a complaint's status while concurrently recording a new entry in complaint_logs—are executed inside an explicit database transaction context (connection.commit()). If an unexpected server failure, disk write exception, or validation error occurs during the sequence, the entire transaction is rolled back (connection.rollback()), preventing partial state mutations where a ticket's status advances without a corresponding audit trail record.

The database connection lifecycle within the Flask application is managed via application context hooks. Connections are created on demand per incoming HTTP request using g._database = get_db() and systematically terminated upon request completion using Flask's @app.teardown_appcontext handler. This connection pooling discipline prevents database lock contention, memory leaks, and unclosed connection leaks that frequently degrade prototype web applications during extended demonstrations.

Data type constraints and check constraints provide an additional defense-in-depth layer directly at the relational storage level. Priority values are strictly constrained to the controlled domain set ('Low', 'Medium', 'High', 'Emergency'), lifecycle status values are restricted to ('Submitted', 'Triaged', 'Assigned', 'In-Progress', 'Resolved', 'Closed', 'Reopened'), and resident feedback ratings are constrained to integer values between 1 and 5. These schema-level validations guarantee that even if an invalid request bypasses application-level form sanitization, the database engine forcefully rejects the malformed record, ensuring unwavering data integrity.

# CHAPTER 4: IMPLEMENTATION

## 4.1 Module Description

The implementation of the Smart Campus Complaint System translates the architectural blueprints, database schema specifications, and security policies established in Chapter 3 into a cohesive, modular web application. The codebase is organized into five decoupled core modules: (1) Authentication and User Profile Module, (2) Grievance Ingestion and Category Tagging Module, (3) Administrative Triage and Work Order Dispatch Module, (4) Field Technician Resolution Desk, and (5) Administrative Analytics Dashboard. Each module encapsulates related route handlers, validation logic, and presentation templates, ensuring high maintainability and testability.

### 4.1.1 Authentication and Student Profile

The Authentication Module manages user registration, credential validation, session initialization, and role verification. User identity is established using institutional email addresses, ensuring that only verified campus community members access internal facility services. Passwords entered during registration undergo client-side complexity checks before transmission over HTTP. On the server, the application computes a cryptographic salted hash using PBKDF2 HMAC-SHA256 with 600,000 hashing rounds via the Werkzeug security library. Plaintext passwords are never written to disk or memory logs.

Upon successful credential verification during login, Flask serializes the user's primary key (id), full name, and authorization role into a signed, cryptographically protected session cookie. The session cookie is configured with Secure, HttpOnly, and SameSite=Lax flags, preventing malicious client scripts from extracting session identifiers and defending against cross-site request forgery attacks. Route decorators (@login_required and @role_required) inspect the session context on every incoming request, redirecting unauthenticated users to the login portal.

To defend against brute-force credential stuffing and dictionary attacks, the authentication controller implements exponential backoff throttling on consecutive failed login attempts. User input sanitization strips leading and trailing whitespace from institutional email strings and normalizes domain cases prior to query execution. The cryptographic password verification routine executes in constant time via hmac.compare_digest, neutralizing side-channel timing attacks that could reveal credential validity through microsecond response variations.

### 4.1.2 Preparation Tracker

The Grievance Intake Module provides students with a streamlined interface for submitting maintenance complaints. The intake form captures four essential attributes: (1) Trade Category selected from a controlled taxonomy (Electrical, Plumbing, Civil Carpentry, HVAC, Campus IT), (2) Precise Location String specifying campus block, hostel wing, floor, and room number (e.g., 'Hostel B, Room 304' or 'Block A, 2nd Floor LH-201'), (3) Issue Title and Descriptive Summary explaining the nature of the fault, and (4) Optional Evidence Media Attachment allowing the upload of a photograph illustrating the defect.

Server-side validation routines inspect the submitted form payload. Text fields are sanitized to remove executable script tags, location strings are checked against minimum length thresholds, and uploaded files undergo strict MIME type verification (.jpg, .jpeg, .png) and size constraint validation (maximum 5 megabytes). Validated files are saved to a secured uploads directory with randomized UUID filenames to prevent filesystem path traversal attacks. Upon successful ingestion, the module generates a unique human-readable ticket code (e.g., 'CMP-2026-0104'), records the ticket in the complaints table with status 'Submitted', and returns the user to their personal tracking dashboard.

The grievance submission workflow incorporates defensive file handling safeguards to prevent arbitrary code execution on the host server. Uploaded image attachments are inspected using Python's imghdr library to verify authentic binary file signatures (magic bytes) rather than relying solely on user-supplied file extensions. Validated files are saved outside the public web root directory, preventing direct script execution, and served exclusively through controlled Flask streaming endpoints with Content-Disposition headers.

### 4.1.3 Mock-Test Tracker

The Administrative Triage Module serves as the operational nerve center for central estate supervisors. It provides an interactive command console displaying all unresolved grievances across the institution. The interface offers multi-parameter filtering, allowing administrators to sort tickets by submission timestamp, trade category, hostel block, or current lifecycle status.

When inspecting a new ticket, the administrator can adjust the assigned priority level—advancing an electrical short circuit or major water leakage to 'Emergency' or 'High'—and designate the trade department responsible for repair. Crucially, the administrator assigns the ticket to a specific on-duty technician chosen from a dynamically populated dropdown menu of trade specialists. Executing this assignment automatically updates the ticket status from 'Submitted' to 'Assigned', records an entry in complaint_logs documenting the supervisor's identity and timestamp, and dispatches the work order to the technician's queue.

### 4.1.4 Company and Placement Tracker

The Field Technician Resolution Desk provides maintenance personnel with a responsive, mobile-optimized console accessible via handheld smartphones and tablets. When technicians log in, the interface displays their personal active work queue, filtering out irrelevant trade requests and displaying only work orders assigned to their technician ID.

For each work order, the technician can review the complainant's room location, contact extension, defect description, and evidence photos. Upon arriving at the repair site, the technician clicks 'Start Repair', advancing the ticket to 'In-Progress'. Following physical completion of the maintenance work, the technician enters descriptive repair notes (e.g., 'Replaced 16A ceramic wall socket and verified voltage stability') and clicks 'Mark Resolved'. This transitions the status to 'Resolved' and triggers an automated verification prompt on the complainant student's dashboard.

The technician interface includes an on-site material requisition logging module. When servicing a facility defect—such as replacing blown circuit fuses, fitting spare ball valves, or resetting network patch panels—the technician selects spare components from a predefined inventory list. This records the exact quantity and trade description of materials consumed directly into the work order record, providing estate management with transparent inventory accounting and preventing material misappropriation.

### 4.1.5 Dashboard

The Administrative Analytics Dashboard aggregates system data into high-level operational metrics to assist estate directors in evaluating facility performance. The module executes optimized SQL aggregate queries to compute total grievances filed, currently active work orders, completed repairs, and average resolution turnaround time across campus departments.

## 4.2 Key Workflows and Processing Logic

### 4.2.1 Authentication Workflow

The authentication workflow governs how user identities are established, validated, and maintained across HTTP request cycles. Because HTTP is inherently stateless, the application maintains state using cryptographically signed session cookies managed by the Flask framework.

When a user submits login credentials, the route handler intercepts the POST request and queries the users table using parameterized SQL. The retrieved password hash is compared against the submitted plaintext password using werkzeug.security.check_password_hash. If the cryptographic comparison succeeds, the session is populated with the user's primary key and authorization role. If the comparison fails, an authentication error is flashed, and the user is redirected without disclosing whether the email or password was invalid, mitigating account enumeration attacks.

### 4.2.2 Create, Read, Update and Delete Operations

Create, Read, Update, and Delete (CRUD) operations across the Smart Campus Complaint System are executed strictly through parameterized SQL queries via Python's standard sqlite3 or mysql.connector database drivers. For grievance creation, an INSERT statement populates the complaints table with validated parameters. For status updates, UPDATE queries mutate the status column while an accompanying INSERT query records the transition in complaint_logs within the same atomic transaction. Ticket deletion is restricted to administrators and is implemented as an archival soft-delete to preserve audit integrity.

To ensure high query performance as the volume of institutional grievance records grows, database tables are structured with targeted composite indexes. Specific B-tree indexes on (user_id, status) and (department_id, status) reduce query execution complexity from full table scans O(N) to logarithmic index lookups O(log N). Dashboard aggregation queries utilize SQL GROUP BY clauses to compute trade summaries in sub-10 millisecond execution times, ensuring responsive user interface rendering even during peak campus usage.

### 4.2.3 Dashboard Aggregation

Dashboard metrics are generated dynamically by querying relational tables using SQL aggregate functions. Total ticket counts are computed using COUNT(id), while category breakdowns utilize GROUP BY department_id. SLA compliance is evaluated by calculating the elapsed time between created_at and updated_at against the designated target hours in the departments table. Work orders exceeding target thresholds without reaching 'Resolved' status are flagged with high-visibility warning badges on the administrative dashboard.

### 4.2.4 Validation Rules

Defensive programming practices are enforced across all user input channels. Form fields enforce maximum character limits and pattern whitelisting. String inputs undergo automatic HTML entity escaping during Jinja2 template rendering, neutralizing stored Cross-Site Scripting (XSS) vectors. File uploads are inspected to verify that filenames do not contain relative directory traversal sequences ('../'), and file extensions are matched against an explicit whitelist of image formats.

These validation rules ensure that malformed or malicious payloads are intercepted at the application controller boundary before interacting with underlying filesystem or database persistence layers.

## 4.3 Implementation Logic

In strict adherence to departmental academic reporting guidelines, this report omits raw programming source code listings, providing instead a comprehensive conceptual description of the underlying implementation algorithms, connection pooling strategies, cryptographic routines, and error handling architectures.

Database connection management is implemented using Flask's application context lifecycle hooks. The application defines a get_db() helper function that lazily initializes a database connection on first access within an active request context and caches the connection handle in Flask's special g object. When the request terminates—whether successfully or due to an unhandled exception—Flask automatically invokes the registered teardown_appcontext callback, executing connection.close(). This design guarantees that database connection leaks are eliminated, ensuring sustained stability during high-volume campus demonstrations.

Cryptographic password verification and data persistence follow defensive security engineering patterns. Password hashing employs PBKDF2 with SHA-256 HMAC iterations and a cryptographically secure 16-byte random salt generated via os.urandom. Database queries strictly utilize the parameterized tuple substitution syntax (cursor.execute('SELECT * FROM users WHERE email = ?', (email,))), ensuring that user inputs are treated exclusively as literal data values rather than executable SQL statements, completely neutralizing SQL injection vulnerabilities.

Error handling across all application endpoints adheres to defensive software engineering principles. Unhandled runtime exceptions—such as database lock timeouts or disk write failures—are intercepted by global Flask @app.errorhandler handlers that display user-friendly, non-technical error notifications while recording detailed stack traces to internal server logs. Database transactions are wrapped in try-except-finally blocks that systematically execute connection.rollback() upon failure, ensuring that the database remains in a consistent, uncorrupted state at all times.

Technicians can no longer mark tickets as resolved without completing the repair, because the student complainant retains final authority to confirm resolution or reopen the ticket. ## 7.2 Limitations

While the Smart Campus Complaint System delivers substantial operational advantages, several technical and architectural limitations must be acknowledged within the context of an introductory academic project.

The primary storage engine utilized during development is SQLite 3. While SQLite provides zero-configuration, transactional reliability perfectly suited for local demonstration and single-department trials, its file-based locking mechanism restricts write concurrency under heavy simultaneous multi-user loads, making it less suitable for campus-wide enterprise deployments without transitioning to client-server databases such as MySQL or PostgreSQL.

A second limitation concerns external notification integration. The current implementation relies on users actively logging into their dashboards to inspect ticket progress. In real-world campus environments, automated external notification channels—such as instant SMS alerts, WhatsApp Business messaging, or institutional push notifications—are highly desirable to alert technicians of emergency dispatches and inform students of repair completions without requiring manual browser refreshes.

A third limitation relates to defect assessment and image analysis. While students can attach photographic evidence documenting facility faults, the system currently treats these attachments as passive media files. The application lacks automated computer-vision capabilities to analyze defect severity, detect duplicate photographs, or automatically suggest trade categories based on image recognition.

Finally, the user interface operates as a standard responsive web application running within a mobile browser. While fully functional, it does not provide offline data caching or native device integration (such as camera access hooks or background sync) that a dedicated Progressive Web App (PWA) or native Android/iOS mobile application would afford maintenance technicians operating in low-connectivity campus basements.

## 7.3 Future Scope

The modular architecture of the Smart Campus Complaint System provides an excellent foundation for substantial future technical extensions across subsequent academic semesters. Planned future enhancements span communication automation, intelligent defect triage, mobile application development, and enterprise infrastructure integration.

First, an automated Multi-Channel Notification Gateway will be integrated using Twilio or Fast2SMS APIs alongside SMTP email services. Whenever an emergency complaint is logged or a technician marks a task resolved, automated SMS and email notifications will be dispatched instantly to the assigned personnel and student resident, minimizing communication delays.

Second, an Intelligent AI Defect Classification Engine can be incorporated using lightweight convolutional neural networks (e.g., MobileNet or ResNet fine-tuned on campus maintenance imagery). The AI model will analyze student-uploaded photos in real time, automatically categorizing defects into Electrical, Plumbing, or Civil trades and recommending appropriate priority ratings, thereby reducing administrative triage overhead.

Third, the web presentation layer will be converted into a Progressive Web App (PWA) equipped with Service Workers and IndexedDB local caching. This enhancement will enable maintenance technicians to view assigned work orders, capture repair photos, and update task notes even in campus basements or remote sports complexes where Wi-Fi and cellular signals are unavailable, automatically synchronizing data once connectivity is restored.

Fourth, the backend persistence layer will be upgraded to PostgreSQL with Redis caching, containerized using Docker, and deployed on institutional cloud infrastructure or high-availability campus servers.
